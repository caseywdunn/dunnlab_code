# Dunn Lab Manuscripts

This skill owns how a manuscript is organized, written, and built, and how results enter it. `dunnlab-biblio` owns citations. `dunnlab-workflow-design` owns the analysis workflow that produces the results. `dunnlab-research-lifecycle` owns scientific readiness and the [publication handoff](../dunnlab-research-lifecycle/references/publication.md) checks.

## The rule: results are generated, never typed

Every number, table, and figure that reports a result is generated by code from the analysis outputs. Neither a person nor an agent types one into the manuscript.

Agents write and revise prose, and write the code that generates results. They do not carry values from analysis output into the text. A value typed by hand is correct only until the analysis is rerun, and nothing marks it as stale when that happens.

An early draft may contain typed values, wrapped as `\placeholder{0.42}` so they can be found. Define `\newcommand{\placeholder}[1]{\textcolor{red}{#1}}` in the preamble, with the `xcolor` package loaded. Replace every placeholder with a generated value before submission.

## Repositories

Each manuscript has two repositories, named as a pair: the analysis repository (`project-a`) holds code and workflow and will eventually be public; the manuscript repository (`project-a-ms`) holds the text and will probably stay private. The manuscript repository is laid out as:

```text
project-a-ms/
├── manuscript.tex
├── references.bib
├── generated/        # copied from the analysis repository; never edited by hand
│   ├── values.tex
│   ├── tables/
│   ├── figures/
│   └── SOURCE        # repository, commit, and date the results came from
├── figures/          # editable sources for hand-assembled figures, if any
├── scripts/          # sync and build scripts
└── tmp/              # gitignored; returned .docx files
```

Results move from the analysis repository into `generated/` by one sync script that records their source. See [Generated results](references/generated-results.md).

## Writing

- **LaTeX is the source of record.** When the target journal is known, start from its LaTeX template. Keep the preamble separate from the content, so that changing journals means changing the preamble, not the text.
- **Use generated values in the text:** `We sampled \nSpecies{} species`. Captions use them too.
- **Include generated tables** with `\input{generated/tables/...}`, keeping the caption and label in `manuscript.tex`.
- **Include figures** without a file extension. See [Figures](references/figures.md).
- **Cite** with `\cite{}` keys from `references.bib`, following `dunnlab-biblio`.

## Building

Render a PDF for reading and a `.docx` for co-authors who edit in Word:

```bash
latexmk -pdf manuscript.tex
pandoc manuscript.tex -o manuscript.docx \
  --citeproc --bibliography references.bib \
  --default-image-extension=png
```

Keep these commands in a build script, together with any journal citation style (`--csl`). Never edit a rendered file; every change goes into the `.tex` source.

After building, check:

- the LaTeX log has no undefined references or citations;
- no `\placeholder` remains, when preparing a submission;
- `generated/SOURCE` names the intended analysis commit; and
- the Word file opens with its figures, tables, and citations intact. Pandoc expands `\newcommand` values and follows `\input`, but complex tables can lose formatting in conversion. Inspect the result rather than assuming it.

## Co-author edits

Co-authors edit the `.docx` with track changes on. Track changes is not for accepting or rejecting edits in Word; it shows exactly what each person changed.

1. Commit the current source.
2. Put the returned `.docx` in `tmp/`.
3. Carry its changes into the `.tex` file.
4. Commit again. The diff between the two commits is the complete record of that co-author's edits; review it, and revert if something went wrong.

**When a co-author changes a generated value or a figure, do not type the new value in.** Flag it instead. It may reflect an error in the analysis, a request for a different analysis, or a misunderstanding, and the fix belongs in the analysis repository.

## Reports are different

[Quarto](https://quarto.org/) suits documents where the analysis is the document, such as analysis reports, supplementary reports, internal summaries, and tutorials. There, executable cells and quick rebuilds matter more than typesetting. The same rule holds: results come from code. Read the workflow's outputs rather than rerunning heavy computation at render time.

## Submission

Use the [publication handoff](../dunnlab-research-lifecycle/references/publication.md) checks: author and contribution information, data and code availability, archived versions, and any AI-use statement. Export figures in the journal's required formats from `generated/figures/` at submission time.
