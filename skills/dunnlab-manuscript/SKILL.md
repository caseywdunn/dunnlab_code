# Dunn Lab Manuscripts

This skill owns how a manuscript is organized, written, and built, and how results enter it. `dunnlab-biblio` owns citations. `dunnlab-workflow-design` owns the analysis workflow that produces the results. `dunnlab-research-lifecycle` owns scientific readiness and the [publication handoff](../dunnlab-research-lifecycle/references/publication.md) checks.

## The rule: results are generated, never typed

Every number, table, and figure that reports a result is generated by code in the analysis repository and enters the manuscript automatically. Neither a person nor an agent types one into the text, and no agent sits on the path that carries a result into the document. A value copied by hand is correct only until the analysis is rerun, and nothing marks it as stale when that happens.

An early draft may mark a value not yet generated as `[[TBD: median length]]`. The pre-render check reports every placeholder; replace them all before submission.

## Two repositories, one direction

Each manuscript has two repositories, named as a pair: the analysis repository (`project-a`), which holds code and workflow and will eventually be public, and the manuscript repository (`project-a-ms`), which holds the text and will probably stay private. Results flow one way:

1. **The analysis repository stages a bundle.** A workflow step writes everything the paper reports into a committed `manuscript/` directory: `values.json`, `tables/`, and `figures/`. The analysis decides what is reported and how it is formatted.
2. **The manuscript repository syncs a pinned copy.** `scripts/sync_results.py` copies the bundle into `_results/` and records the analysis commit it came from. The sync is committed on its own, so its diff shows exactly which numbers and figures changed.
3. **Quarto reads `_results/` with no code execution.** Values come in through Quarto's `meta` shortcode, tables through `include`, and figures by path. Rendering needs only Quarto and a LaTeX distribution.

See [The results bundle](references/results-bundle.md) for the bundle's layout and the scripts, and [Figures](references/figures.md) for figure conventions.

```text
project-a-ms/
├── manuscript.qmd
├── _quarto.yml
├── references.bib
├── _results/         # synced from project-a/manuscript/; never edited by hand
├── figures/          # editable sources for hand-assembled figures, if any
├── scripts/
│   ├── sync_results.py
│   └── check_results.py
└── tmp/              # gitignored; returned .docx files
```

## Setting up

Copy the templates in this skill: `templates/manuscript/` into the manuscript repository, and `templates/analysis/write_manuscript_values.py` into the analysis repository's `scripts/`. Set `DEFAULT_ANALYSIS_REPO` in `sync_results.py`. When the target journal is known, add its Quarto journal extension (for example from [quarto-journals](https://github.com/quarto-journals)) rather than hand-building a LaTeX template.

## Writing

Quarto Markdown (`.qmd`) is the source of record:

```markdown
We sampled {{< meta results.n_species >}} species (@tbl-sampling; @fig-tree).

{{< include _results/tables/sampling.md >}}

: Taxon sampling of {{< meta results.n_species >}} species {#tbl-sampling}

![Phylogeny of {{< meta results.n_species >}} species.](_results/figures/tree){#fig-tree}

Code and results are archived at doi:{{< meta analysis.doi >}}.
```

- Values work in captions as well as text.
- Include vector figures without a file extension, so each output format picks its own file; include raster-only figures, such as micrographs, as `.png`. See [Figures](references/figures.md).
- Cite with `[@key]` from `references.bib`, following `dunnlab-biblio`.
- The `analysis` block of `values.json` supplies the repository URL, commit, version, and DOI for data-availability statements.

## Building

```bash
python3 scripts/sync_results.py   # when the analysis bundle has changed; then commit _results/
quarto render --to all            # PDF (plus its .tex source) and Word
```

Every render first runs `scripts/check_results.py`. It fails the render if the text uses a value, table, or figure missing from `_results/`, and warns about placeholders, about results generated from uncommitted analysis code, and about an analysis bundle that has changed since the last sync. Never edit a rendered file; every change goes into the `.qmd` source.

## Co-author edits

Co-authors edit the `.docx` with track changes on. Track changes is not for accepting or rejecting edits in Word; it shows exactly what each person changed.

1. Commit the current source.
2. Put the returned `.docx` in `tmp/`.
3. Carry its changes into the `.qmd` file.
4. Commit again. The diff between the two commits is the complete record of that co-author's edits; review it, and revert if something went wrong.

**When a co-author changes a generated value or a figure, do not type the new value in.** Flag it instead. It may reflect an error in the analysis, a request for a different analysis, or a misunderstanding, and the fix belongs in the analysis repository.

## Submission

Use the [publication handoff](../dunnlab-research-lifecycle/references/publication.md) checks: author and contribution information, data and code availability, archived versions, and any AI-use statement. Confirm that `_results/` was synced from the archived analysis release and that the pre-render check reports no placeholders. Export figures in the journal's required formats from the bundle at submission time.
