# Figures

Figures are generated by the analysis code into the bundle's `figures/` directory, synced into the manuscript's `_results/figures/` with the other results, and included by path. The aim is that rerunning the analysis and syncing updates every figure, with no manual step, wherever the figure's content allows.

## Generate at final size

Make each figure at the size it will be printed, so that text and line widths in the code are what readers see. Do not scale figures in the manuscript.

- **Widths:** a single journal column is typically about 85–90 mm, and a full page width about 170–180 mm. Check the target journal. Set the size in the plotting code; matplotlib takes inches, so divide millimetres by 25.4.
- **Text:** at least 6–7 pt at final size, in a font the journal accepts.
- **Color:** use colorblind-safe palettes, and give the same entity, such as a species or treatment, the same color in every figure. Define the palette once in the analysis code.
- **Panels:** assemble multi-panel figures in code where possible, with matplotlib subfigures or `GridSpec`, or `patchwork` in R, including the panel letters.

## Vector by default

Figures in the manuscript are vector graphics, so lines and text stay sharp at any zoom and journals can scale them. The exception is a layer with a very large number of elements, such as a scatter plot of a million points or the edges of a large graph: as vectors these make files that are huge and slow to open. Rasterize **only that layer**, keeping axes, labels, and text vector:

- **matplotlib:** pass `rasterized=True` to the dense artist, as in `ax.scatter(x, y, rasterized=True)`, or call `ax.set_rasterization_zorder(z)` to rasterize everything drawn below a given layer. The `dpi` given to `savefig` sets the resolution of the rasterized layer; use 300 to 600.
- **Datashader,** for millions of points or more: it renders the dense layer to an image, which matplotlib places within vector axes.
- **R:** the `ggrastr` package rasterizes individual ggplot layers, for example `geom_point_rast()`.

Check the result by zooming in on the PDF: text and axes should stay crisp, and only the dense layer should pixelate.

## Two files per figure

Save each figure twice, with the same base name:

- **`tree.pdf`**, the vector file used in the PDF manuscript. Embed fonts; in matplotlib, set `pdf.fonttype` to 42.
- **`tree.png`**, a raster copy for the Word version, at 300 dpi or more, or 600 dpi for line art. Word cannot display PDF images, so the PNG is what co-authors editing in Word see.

**Raster images**, such as micrographs and photographs, have no vector form. Save them once, as a PNG at their native resolution, converting TIFF to PNG in the analysis, since neither LaTeX nor Word reliably displays TIFF. Include them with the `.png` extension, as below.

## Include without an extension

```markdown
![Phylogeny of {{< meta results.n_species >}} species.](_results/figures/tree){#fig-tree}
```

With no extension, each output format chooses its file through `default-image-extension` in `_quarto.yml`: `pdf` for the PDF build and `png` for Word. The pre-render check therefore requires both files. A raster-only figure is included with its extension, which both formats accept:

```markdown
![In situ hybridization of the gene in a tentacle.](_results/figures/in_situ.png){#fig-in-situ}
```

## Figures assembled by hand

Some figures need hand work: photographs, illustrations, or annotations combined with generated panels. For these:

- keep the editable source, such as an Inkscape SVG or an Illustrator file, in the manuscript repository's `figures/`;
- link the generated panels into it where the tool supports linking, rather than pasting copies;
- re-export the figure after every results sync, and treat that as a listed build step rather than something to remember; and
- note in the figure's source file or a README which generated panels it uses.

A hand-assembled figure is the one place where a stale result can hide. Keep the hand work to layout and annotation, and leave every plotted value to the code.

## Submission

Journals often want figures as separate files in specific formats, such as TIFF or EPS, and at specific resolutions. Export them from the bundle's files at submission time rather than keeping a second set in the repository.
